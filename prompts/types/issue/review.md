# Issue 검수 단계

work type이 Issue인 ticket을 검수 모드에서 처리하는 단계를 정한다. 각 단계가 가리키는 절과 파일을 함께 적용한다.

---

## 검수 단계

1. description.wiki에서 사람 구역(이슈 유형, 이슈 내용)을 읽는다.
2. 아래 "완료 판단 기준"으로 사람의 기록에서 대응 결과와 그 근거를 찾는다.
3. work type 공통 파일의 "tldr 형식"으로 TL;DR의 대응 결과를 작성한다. 마지막 항목의 검수 결과는 7단계에서 정한 값으로 채운다.
4. 사람 구역에 없는 유용한 링크가 있으면 work type 공통 파일의 "링크 추가 요청 문장"으로 requests에 적는다.
5. 아래 "검사 항목" 표의 검사와 `prompts/review.md`의 "공통 검사 항목"을 모두 checks에 넣는다.
   - 계산 주체가 스크립트인 검사(I1, I2)는 precheck.json의 결과를 그대로 인용한다. I1이 unknown(스크립트가 체크박스 상태를 확인하지 못한 결과)이면 표 아래 규칙으로 판단한다.
   - I3은 CI agent가 3단계에서 작성한 TL;DR로 판단한다.
6. 아래 "문서화 리뷰" 기준표로 I4, I5를 판단해 checks에 넣고, `prompts/review.md`의 "문서화 리뷰 feedback 작성" 절에 따라 feedback을 작성한다.
7. 아래 "검수 결과" 절과 `prompts/review.md`의 "검수 결과 코드값의 공통 기준"으로 검수 결과 코드값(verdict.verdict)을 정한다.
8. 아래 "comment (결과 요약 부분만)" 절과 `prompts/review.md`의 "결과 요약(comment) 작성" 절에 따라 tasks[].comment를 작성한다.

---

## 완료 판단 기준

대응 결과가 근거와 함께 있어야 한다(대응 결과의 근거 (I3)).
- 대응 결과는 수용, 반려, 다른 ticket으로 이관 중 하나이며 이유 한 줄이 있어야 한다.
- 근거는 결정을 적은 comment의 링크, 또는 이관해서 만든 ticket의 키다.

---

## 검사 항목

| ID | 이름 | 검사 내용 | 계산 주체 | 검수 모드 영향 |
|---|---|---|---|---|
| I1 | 이슈 유형 선택 | 이슈 유형 체크박스가 1개 이상 선택됨 (precheck가 unknown이면 CI agent가 description 원문으로 판단) | 스크립트, 보조로 CI agent | 실패 시 보류 |
| I2 | 이슈 내용 작성 | 이슈 내용이 있음 | 스크립트 | 실패 시 보류 |
| I3 | 대응 결과의 근거 | TL;DR의 대응 결과에 근거(comment 링크 또는 만들어진 ticket 키)가 있음 | CI agent | 실패 시 보류 |
| I4 | 이슈 내용 충실도 | 아래 "문서화 리뷰" 참고 | CI agent | 문서화 리뷰 정책 |
| I5 | 논의와 결정 기록 | 아래 "문서화 리뷰" 참고 | CI agent | 문서화 리뷰 정책 |

- 이 표 외에 `prompts/review.md`의 공통 검사 항목(R2, R3, R4)도 checks에 넣는다.

- precheck.json(`scripts/precheck.py`가 계산한 검사 결과 파일)의 이슈 유형 선택 (I1) 결과가 unknown이면, description.wiki의 이슈 유형 구역을 직접 읽어 선택된 항목이 있는지 판단한다.
  - unknown은 스크립트가 체크박스 상태를 텍스트로 확인할 수 없을 때의 결과다(`scripts/src/jira/precheck/template.py`의 `check_issue_template`).
  - 이슈 유형 체크박스에서 선택한 항목은 description.wiki에 취소선(예: `-제안-`)으로 나온다(INNO-36 시험 실행, 2026-10-08). 취소선 항목이 있으면 선택된 것으로 판단한다.

## 문서화 리뷰

| ID | pass 기준 | fail 예 |
|---|---|---|
| I4 이슈 내용 충실도 | 왜 제기했는지(문제, 근거 수치)와 결정이 필요한 것이 이슈 내용에 있음 | 요구만 있고 이유가 없음 |
| I5 논의와 결정 기록 | 검토한 대안이나 의견과 결정 이유가 comment에 있음 | 결정만 있고 이유가 없음 |

대응 결과의 근거 (I3)는 결정을 적은 근거가 있는지를, I5는 결정에 이른 논의와 이유가 충실한지를 판단한다.

```json
"feedback": [
  { "id": "I4", "points": ["추론 서버의 GPU 메모리 부족으로 요청이 실패한 사례와 결정이 필요한 것(서버 증설 또는 모델 경량화)이 이슈 내용에 있어 제기한 이유가 분명함"] },
  { "id": "I5", "points": ["이관 결정 comment([comment 2026-09-20|https://<site>/browse/INNO-40?focusedCommentId=10300])에 결정만 있고 검토한 대안(서버 증설, 모델 경량화)과 이관을 고른 이유가 없음"],
    "request": "검토한 대안과 이관을 결정한 이유 comment 필요" }
]
```

---

## comment (결과 요약 부분만)

대응 결과가 무엇이고 어디에 근거가 있는지를 개조식 1–3줄로 적는다.
- 줄마다 근거 wiki 링크([comment 날짜|URL]) 또는 이관해서 만든 ticket의 키를 붙인다.

---

## 검수 결과

- R3은 검수 결과에 영향이 없어 아래 조건에 넣지 않는다.
- pass(통과): 아래 검사가 모두 pass 또는 n/a다.
  - I1
  - I2
  - I3
  - R2의 링크 기준(agent 구역의 결과마다 확인 가능한 링크가 있음)
  - R4
- fix(보류): 아래 검사 중 fail이 있다.
  - I1
  - I2
  - I3
  - R2의 링크 기준
  - R4
- escalate(검토 요청): 대응 결과가 comment마다 다르게 적혀 있어 무엇이 최종인지 알 수 없다.
